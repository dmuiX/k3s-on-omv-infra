# Temporary gateway backport: Envoy #48409

The close-wakeup change in [Envoy PR 48409](https://github.com/envoyproxy/envoy/pull/48409) addresses a blocked writer on internal socket close. Its merge into Envoy main does **not** mean an Istio release contains it. `48409.patch` and `regression.patch` carry the upstream Apache-2.0 source change and regression coverage for the pinned Istio 1.32.0 source. CI does not contact Kubernetes, operate a registry on the LAN, or ship credentials in the build container.

## Activation and build flow

- Disabled by default. Configure `ENVOY_RUNNER_AMD64` and `ENVOY_RUNNER_ARM64` as native, dedicated, ephemeral GitHub-hosted Linux runner labels (Docker, 100 GiB free minimum, adequate CPU and RAM). Do not use production nodes or private-LAN runners. These are long, potentially billable C++ builds. Set `ENVOY_BACKPORT_ENABLED=true` only after reviewing runner budget and package permissions. The repo must permit GitHub Actions to create PRs and publish the candidate package; verify it is pullable by nodes before promotion.
- Dispatch on `main`, or merge a reviewed backport/lock change. The daily release check can build a newer **stable patch in the configured Istio minor series** on both architectures. Minor upgrades and incompatible layouts require review. The updater opens a lock-only PR for a new Istio release; it never upgrades the control plane. A change to the control-plane pins retriggers the build. If the pins differ, the image override is not proposed.
- For each architecture, verify the proxy and Envoy archive digests; apply the regression tests and run against stock source first. Only the expected failing test authorizes applying the backport. Require passing tests and a successful image smoke test. If the stock source passes with no functional backport, select the official image. An incompatible test overlay that neither applies cleanly nor is already present fails closed; refresh the tests/adapters after inspecting the release rather than treating patch conflicts as proof of a fix.
- Both architectures must agree. For a patched candidate, publish native images and a combined digest under `ghcr.io/dmuix/istio-proxyv2`. For stock, remove **only** the managed override and comment. Nothing targets a floating registry tag in the deployment. No publish event by itself is a production promotion.

## Before merging a generated deployment PR

Scan the candidate, confirm both native manifests and stock compatibility with the deployed revision, then verify actual playback, seeking, and stream drain on an isolated gateway using the exact proposed artifact. Do not merge on unit tests or `/ping` alone. Without a reproducible baseline, record the inconclusive result. A GitOps merge can roll all replicas: for a production canary, stage a distinct gateway before promoting the shared deployment. Rollback is a revert to the last verified digest/configuration. The workflow deliberately creates draft PRs; it does not approve itself, enable auto-merge, or access a production kubeconfig.
