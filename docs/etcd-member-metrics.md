# Draft: scrape native etcd member metrics privately

All three K3s servers are etcd members. Each serves native member metrics on `127.0.0.1:2381/metrics`; none is currently scraped by either Prometheus replica. The `etcd_request_duration_seconds` API-server client histogram is not member telemetry. For the pinned [K3s release](https://github.com/k3s-io/k3s/blob/v1.37.1%2Bk3s1/pkg/etcd/etcd.go), enabling `etcd-expose-metrics` also opens a plaintext node listener. Leave it disabled, and do not use the etcd client port (2379), peer port (2380), datastore keys or a public route for monitoring.

**Proposed path:** `Prometheus -> private node address:dedicated HTTPS port (client certificate required) -> GET /metrics on 127.0.0.1:2381`. This is a design, not a listening service. Before choosing a proxy, inventory existing maintained host TLS listeners and certificate delivery. Reuse one only if it can enforce the dedicated bind address, exact method/path and client identity independently. Otherwise evaluate a minimal supported host reverse proxy; do not introduce a CA or wildcard listener implicitly.

1. **Bootstrap ownership:** reserve an unused private monitoring port, configure one listener on each etcd-role host, permit only `GET /metrics`, and deny forwarding to any other path/port. Automate certificate issuance, renewal/reload and removal. Use a dedicated monitoring trust boundary/client identity, verified node certificate SANs, and no cluster-admin or etcd credentials. Determine actual scrape source addresses after NAT before restricting host firewalls; never rely on source addresses alone. Keep local recovery independent of this listener.
2. **Infra/Live ownership:** use the existing `kubeEtcd` ServiceMonitor rather than adding a second etcd job. In the pinned chart set `kubeEtcd.endpoints` to the three etcd-role inventory addresses in Live, set Service port and targetPort to the new listener, and configure the ServiceMonitor for HTTPS with verified server name, CA and client certificate/key references. Explicitly set `kubeEtcd.serviceMonitor.authorization: null` to remove the chart default: the rendered endpoint must have `tlsConfig` but no `authorization` or bearer-token fields. Never forward the Prometheus Kubernetes token to a host listener. Choose certificate SANs and `serverName` compatible with all static targets. Validate the rendered endpoints, port names and Prometheus namespace access to the TLS material. Never embed keys in Git or disable verification.
3. **Acceptance:** before each next member, verify that unauthorized clients cannot scrape and approved clients cannot access non-metrics paths. On **each** Prometheus replica require three distinct etcd targets up, `etcd_server_has_leader == 1` from all three members, one leader under steady state, and populated WAL fsync histograms. Add an expected-members coverage alert independent of the discovered target count (a missing job must not look healthy). Rehearse certificate renewal and failure handling; check latency and error alerts with offline rule tests. Do not trigger an etcd election as a test.

**Decision gate:** agree on TLS ownership and rotation before opening any port. No node restart or change to datastore quorum is intended. Roll back the monitoring targets, private listeners and dedicated firewall rules/credentials without touching etcd membership, its stored data, or its peers.
