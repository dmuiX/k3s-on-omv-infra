# Native etcd member metrics (#109)

All three K3s servers are embedded-etcd members, including the server without API-server workloads. The member endpoint is `http://127.0.0.1:2381/metrics`. This collection path is independent of K3s component scraping (#108); the API server's `etcd_request_duration_seconds` is a client histogram, not a member measurement.

**Data path:** a Bootstrap-managed systemd timer on each member → one local `GET /metrics` every 30 seconds → atomic replacement of `/var/lib/etcd-member-metrics/member.prom` → the existing node-exporter textfile collector → both Prometheus replicas via their existing node-exporter ServiceMonitor. The three files need no host label: the existing scrape target supplies `instance`.

Only two native leader gauges, the failed proposals counter and the WAL fsync histogram (including buckets, sum and count) are published. The file also contains `platform_etcd_member_last_success_timestamp_seconds`. The unprivileged helper replaces the file only after validating one complete response; a failed GET or invalid sample cannot renew the timestamp. No upstream comments, identities, addresses, arbitrary labels or raw response files are exported. The exporter mounts the dedicated directory read-only. An empty directory on a non-member is normal.

**Why not the draft TLS proxy?** These selected metrics can have the same audience as the existing node metrics. The textfile collector needs no proxy, scrape job, certificate lifecycle, host firewall change, node addresses in Git, Kubernetes `nodes/proxy` permission or datastore keys. This does **not** authenticate the existing exporter or make it private via ambient mTLS; anyone who can already scrape it can read the selected metrics. Do not deploy if that audience is inappropriate. Do not enable `etcd-expose-metrics` (the [pinned K3s implementation](https://github.com/k3s-io/k3s/blob/v1.37.1%2Bk3s1/pkg/etcd/etcd.go) would expose a plaintext listener), modify the chart's etcd targets, or scrape the client or peer ports.

## Rollout and acceptance (not performed by CI)

1. In the paired Bootstrap repo, follow `docs/ETCD-MEMBER-METRICS.md` for `ansible/maintenance/configure-etcd-member-metrics.yml`. Install on one member first. Check the timestamp advances, file/parent permissions permit exporter reads, clocks are synchronized, and etcd metrics remain loopback-only. Repeat on the other two members. No K3s service restart or etcd membership change is needed.
2. Review the effective node-exporter Service and access restrictions: no new route or listener should be needed. Check site overrides for conflicting extra arguments/mounts or scrape relabelings before syncing Infra. The chart change rolls only the exporter pods; the existing node-exporter filesystem exclusions and ordinary host metrics stay in place.
3. On **each** Prometheus replica, check that all three node-exporter targets are up, `node_textfile_scrape_error{job="node-exporter",namespace="node-exporter"}` is zero and `platform_etcd_member:reporting_members` equals **3**. This recording rule counts distinct instances only when up, both leader gauges exist, and the success timestamp is at most 120 seconds old and not in the future. To identify a stale file, inspect `time() - platform_etcd_member_last_success_timestamp_seconds{job="node-exporter",namespace="node-exporter"}` by instance; compare missing series to member inventory, not just discovered targets.
4. In steady state require `etcd_server_has_leader{job="node-exporter",namespace="node-exporter"}` to be 1 on every member and exactly one `etcd_server_is_leader` to be 1 with the same selector. Check all three have populated `etcd_disk_wal_fsync_duration_seconds_bucket` series and advancing `_count` values under writes. Confirm the [member rules](../09-kube-prometheus-stack/resources/etcd-member-alerts.yaml) are loaded and evaluating on both replicas. Alert evaluation is distinct from notification delivery (the public Alertmanager default has zero replicas).

Missing/stale/down input is a **telemetry** alert, not proof of leader loss. The coverage requirement is fixed at three, independent of discovery; review it if membership changes. Failed proposals and sustained slow WAL fsync are evaluated only for fresh members. CI exercises loss of one target, loss of the entire job, stale and future timestamps, duplicate scrapes, leader anomalies and latency/errors using `promtool`; do not force an election or disrupt quorum to test alerts.

**Rollback:** revert the exporter argument/mount and member rules in Infra. Automated pruning is off: explicitly retire only `PrometheusRule/etcd-member-alerts` in `kube-prometheus-stack` after it leaves desired state. Verify normal node metrics still arrive, then follow the Bootstrap runbook to stop the timer and remove its dedicated files/account. Never remove existing exporter resources, change etcd listeners or touch datastore contents as part of rollback.
