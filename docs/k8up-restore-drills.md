# K8up repository restore drills

| Namespace | Source in the OMV repository | Pass condition | Weekly schedule (Europe/Berlin) |
|---|---|---|---|
| `backup-validation` | Backed-up `k8up-validation-canary` PVC, snapshot no older than 48h | Exact restored bytes of `marker.txt` | Tuesday 09:15 |
| `kube-prometheus-stack` | Native replica-0 TSDB snapshot streamed by the K8up PreBackupPod, no older than 8 days | Verified Restic restore, validated tar, then a real historical node-info sample read by promtool | Tuesday 12:15 |

Both `k8up-restore-drill` CronJobs and the one-time seed Job ship **suspended**. These are the two configured K8up sources, not a generic restore of every namespace. The canary is a fixture; only the TSDB source exercises production data. No Prometheus backup is created by this drill. Follow the [native backup runbook](prometheus-tsdb-backup-runbook.md) before the first TSDB drill. New sources must declare a source/path, freshness and meaningful verifier. PostgreSQL, OpenBao, etcd and Audiobookshelf use other backup paths.

**Why not just a K8up Check or Schedule.restore?** A repository Check does not open the application data. The pinned [K8up 2.16 Schedule API](https://github.com/k8up-io/k8up/blob/v2.16.0/api/v1/schedule_types.go) can schedule a Restore, but has no condition-gated application verifier sharing its disposable target. Instead, one Kubernetes Job uses the Restic client shipped in the pinned K8up image, with a read-only repository mount, `--no-lock --no-cache`, an exact snapshot ID and `restore --verify`. Only the restore init container receives the repository password reference. The next container checks the restored files; the Prometheus template additionally runs the version-matched TSDB reader. No live database mount, Ingress, Service, service-account token, or cleanup controller is needed.

## Rollout and acceptance

1. **Sync the private Live policy companion first**, then both Infra Applications. Confirm the exact drill/seed labels are excluded from the general validation namespace allows, that the isolation policy selects the Pods, and that no injected sidecar or other additive policy changes their access. Check source PVC bindings, UID 1000 read access to the retained SMB repository, and free encrypted strict-local Longhorn space (256 MiB canary / 48 GiB TSDB). The drills must not overlap repository prune/maintenance: `--no-lock` is used because the repository is read-only. Coordinate manual runs too.
2. For the fixture only, release `backup-validation/k8up-canary-seed-v1` in Git in a maintenance window. It creates the known marker without replacing conflicting data. Wait for successful completion and RWO unmount, then a fresh backup of that PVC and a successful repository check. For Prometheus obtain a fresh tagged backup and successful check as above. A missing/stale or mismatched snapshot is a **failure**, not a skipped test. The observed monitoring namespace had no Snapshot or Backup CR when this change was written; this is not evidence its OMV repository is empty.
3. With operator approval, clone **one** suspended CronJob at a time as a uniquely named Job (e.g. `kubectl -n backup-validation create job k8up-canary-drill-<run-id> --from=cronjob/k8up-restore-drill`). Observe the selected snapshot ID/time and terminal verification result in the respective container logs and Job condition. Record this bounded evidence before TTL, not raw application contents. Require `Complete=True`, not merely a successful restore init container.
4. Record the drill Pod's **own** ephemeral PVC UID, bound PV and CSI handle; check `longhorn-restore-test`, `Delete` and `k8up.io/backup: 'false'`. After the Job TTL (one hour), verify that this exact Pod, PVC, PV and Longhorn volume disappear on success and failure. Never force a finalizer or delete another run's resources. Only then enable each schedule by reviewed change. The fixture and both retained repository PVCs are deliberately not cleaned up.

Rollback: suspend both drills; allow outstanding Jobs and their TTL cleanup to finish. Revert the Infra changes before widening any Live selector. With prune disabled, retire only the newly added drill CronJobs, completed seed and drill-only configuration/policies once unused. Preserve sources, repositories, backup schedules and credentials.
