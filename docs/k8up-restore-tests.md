# K8up repository restore tests

| Namespace | Source in the OMV repository | Pass condition | Schedule (Europe/Berlin) |
|---|---|---|---|
| `backup-validation` | Synthetic `k8up-validation-canary` PVC | Restore the exact successful run's snapshot ID and compare `marker.txt` byte for byte | Daily at 09:15 (suspended pending cutover) |
| `kube-prometheus-stack` | Native replica-0 TSDB snapshot streamed by the K8up PreBackupPod | Verified Restic restore, validated tar, then a real historical node-info sample read by promtool | Daily at 11:55 (suspended pending rollout) |

`backup-validation/k8up-backup-validation` is the fixture runner. Its seed and verifier CronJobs (`k8up-canary-seed-template`, `k8up-backup-validation-verify`) are **permanently suspended Job templates**, not schedules to enable. The separate [Prometheus pipeline](prometheus-tsdb-backup-runbook.md) and its rollout are unchanged. A suspended CronJob can be `Healthy` in Argo CD; this is not evidence of verification. PostgreSQL, OpenBao, etcd and Audiobookshelf use other backup paths.

## Exact fixture continuation

1. The runner checks the approved repository fence, absence of **all** native K8up `Schedule` objects (including ones being deleted), absence of unfinished K8up operations and child Jobs, and the fixed source and PodConfig. It creates no work if any gate fails.
2. It creates its seed Job from the suspended template. The tokenless, network-isolated seed reuses `seed.py` to write or verify the marker on the existing synthetic PVC without overwriting data. It mounts no repository. The runner waits for that Job UID to complete before submitting the Backup, so its Pod is no longer using the RWO volume when K8up requests attachment. The runner itself mounts neither PVC nor repository credentials.
3. It submits one K8up Backup with the fixed canary label selector, fixed local SMB repository and static `fixture-k8up-omv-v1` PodConfig. The two tags are `k8up-validation-canary` and `backup-run-<runner Pod UID>`. Only after that exact Backup UID reports `Completed=True` with `reason=Succeeded` does it submit and wait for a Check of the same repository.
4. It creates its verifier Job from the suspended template, passing only that run tag. The offline restore init container requires one fresh Restic match with host `backup-validation`, only the path `/data/k8up-validation-canary`, and exactly the two expected tags. It logs the full ID and restores that ID with `restic restore --verify` into fresh scratch. A missing, stale, duplicate, wrong-source or wrong-tag artifact fails; there is no `latest` fallback. The marker verifier reads only scratch. Success requires the same verifier Job UID to report `Complete=True`; `stage=fixture-pipeline result=PASS` logs all four child UIDs and the run tag.

K8up's Check alone does not exercise the restored data. The pinned K8up Schedule API also has no success-gated application verifier sharing the restore target. The local repository is read-only in the verifier, so Restic cannot write a lock there. The activation fence below, not schedule timing, excludes maintenance from that repository while the automatic verifier may run.

## Fixture cutover (separate approval, not part of this change)

The existing Live `backup-validation/validation` K8up Schedule and its Backup/Check/Prune continue unchanged on sync. The new runner ships suspended and its namespace has no `platform.k3s-on-omv.io/fixture-pipeline=enabled` opt-in. Keep it this way until all gates are satisfied. Syncing the inactive policies does not change admission for the existing K8up operations or general workloads; fixture runner creates are denied until opt-in.

1. Verify the Infra and Live network policies exclude `app.kubernetes.io/name: k8up-restore-test` from general API, HTTPS, DNS, metrics and other grants. Only the additional `fixture-runner: 'true'` label gets the Infra API tuples; neither child gets them. Verify no injected proxy or additive policies give the children access. Check the same retained SMB repository and secret reference are used throughout, that the repository is not used by any other namespace or direct SMB/Restic writer, and that the read-only mount is readable by UID 1000. Check Longhorn CSI, schedulable 256 MiB encrypted strict-local scratch with `Delete` reclaim policy, and the canary's RWO attachment. Do not enable if any gate is unverified.
2. In a coordinated, separately approved cutover, stop the native Schedule in Git and retire its live object after verifying namespace, ownership and UID (`prune: false` will not retire it automatically). Let K8up finish deletion, including its Schedule finalizer. Drain its Backup/Check/Prune workers and any maintenance outside K8up. Stop manual seed/restore use and drain any old Jobs and Pods, including residual `k8up-restore-test` CronJobs from earlier revisions; verify their ownership and retire only those obsolete CronJobs. Do not select resources for deletion by their shared Pod label and do not remove finalizers to force progress. The fixture runner fails closed if it still sees a Schedule or nonterminal operation; review any stale resources rather than bypassing the gate.
3. Still with the runner suspended, arm the reviewed namespace label. In the armed namespace the admission fence denies new native Schedules and K8up operations other than the fixture runner's exact Backup and Check. It also denies new batch Jobs with K8up's native `k8up.io/type: prune` label, even if a delayed reconcile came from a Prune admitted before opt-in. It protects the fixed source label and PodConfig. The runner's Job create permission is bounded by fail-closed admission to clones of the matching suspended templates. Confirm admission with isolated native API testing and verify the cutover protections have taken effect before enabling. Keep the label and all bindings in force until the runner and every child are drained; the fence does not control administrators, alternate mounts, or direct repository access outside the approved workflow.
4. Only then enable the runner in a reviewed change. Observe its normal scheduled run, not a manually seeded or cloned run. Record the run tag, UIDs, verifier's selected snapshot ID/time and terminal marker validation. Confirm TTL reclaims the exact verifier Job, Pod, ephemeral PVC, PV and Longhorn volume on success and failure. Do not use the retained fixture PVC or repository as scratch.

The old Schedule's automated retention **does not run while the fence is armed**. Before enabling, agree on capacity and separately coordinated maintenance: suspend the runner and drain all parent and child operations before disarming the fence or running Prune. A cutover that needs unattended Prune as well is not covered by this daily fixture pipeline. For rollback, suspend and drain first, keep child network exclusions intact, disarm the fence only after all children are gone, then restore the approved native Schedule. No alternate backup path or destination is introduced.
