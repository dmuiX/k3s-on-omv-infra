# Backup contract

| Data | Native backup | OMV directory | R2 |
|---|---|---|---|
| PostgreSQL | Barman Cloud | `cloudnativepg-backups` | `cloudnativepg-backups` |
| OpenBao | Raft snapshot adapter | `openbao-backups` | `openbao-backups` |
| Future application PVCs | K8up/Restic | `<namespace>/<repository-pvc>` | Never |
| etcd | native K3s snapshot | `etcd-backups` | `etcd-backups` |
| Prometheus | Native TSDB snapshot, then one-shot K8up Backup | `kube-prometheus-stack/prometheus-k8up-repository` | Never |

All OMV storage is beneath the dedicated `k3s-cluster` Btrfs subvolume on the verified backup filesystem. The Live StorageClass source is exactly `//192.168.1.5/k3s-cluster`. Verify that the backing disk and SMB share are available; never create a substitute directory on the root filesystem. PostgreSQL/OpenBao PVCs are excluded from generic K8up backups. Longhorn replication is not backup.

The `postgresql-r2-backup-budget-preview` CronJob runs daily in dry-run mode. The 4 GiB budget covers PostgreSQL base backups in R2, not WAL or total bucket usage. Missing or failed PITR/mirror evidence still blocks the job. With valid evidence it reads Barman's timezone-aware `end_time_iso` and checks each backup's native keep status; it does not delete base backups or WAL. Monitor storage growth while previewing. Do not enable `run --apply` until a current production restore succeeds and an isolated retention rehearsal confirms the deletion scope and recoverability of retained backups. Switching modes requires a separate reviewed manifest change.

**CronJob rename:** With automated pruning disabled, Argo CD does not remove the old `cloudnative-pg/postgresql-size-retention` CronJob. Before an approved merge, hold the root `infra` Application, then disable auto-sync on `k3s-postgres` and confirm neither has a queued or running sync. Verify the old CronJob's ownership and UID, suspend it and let its Jobs finish before syncing the replacement. Confirm the replacement uses `--dry-run`, then retire only the old CronJob before resuming reconciliation. The ServiceAccount, RBAC and adapter keep their existing identities and must not be removed as part of the rename.

For the November 2026 WAL-retention incident, recovery gates and the planned December CNPG update follow-up, see [PostgreSQL WAL recovery](postgresql-wal-recovery.md).

## Disposable PITR storage

The temporary `backup-validation/postgresql-pitr-validation` Cluster requests the non-default `longhorn-single-node-delete` class, replacing `longhorn-restore-test` for new validation PVCs. Its 5 GiB working copy has the same encryption and local placement as `longhorn-single-node-retain`, but its PV uses `Delete`. CNPG propagates `k8up.io/backup: "false"` so generic backups should not mount the disposable PVC. The validator requests deletion of its temporary Cluster and ObjectStore using UID preconditions. If a create response is ambiguous, it polls only that resource's exact name for up to 60 seconds and deletes it only if it has a UID and bears the current run's annotation. An `AlreadyExists` collision is left untouched. If the resource is still not found at the deadline, the validator logs the unresolved create and reports `failed-cleanup`; the create may still complete later. Normal owner-reference and CSI cleanup reclaims the disk **after** the PVC is released. A killed Job or an in-use PVC can delay or prevent cleanup. Never force a finalizer. Production PVCs, the mirror, backups and existing retained PVs are unchanged.

Before merging the validator switch, verify the new class exists, no restore validation Job is active, and the next scheduled run is not imminent. Sync the CronJob and its ConfigMap together: the entrypoint and ConfigMap key both change to `postgresql_restore_test.py`. Before the first new run, verify the validator ConfigMap uses it. Record the new PVC UID/PV handle and verify the annotation, reclaim policy and eventual removal of that PVC, PV and Longhorn volume. Reverting the validator affects future claims only; it cannot restore a deleted scratch disk. Keep the class until outstanding claims have finished.

## PITR validator startup

Only the first connection to the source PostgreSQL service retries `server closed the connection unexpectedly`: up to four attempts with 1, 2 and 4 seconds between attempts. Authentication errors, SQL statements and later connections are not retried. If the first connection never opens, the status Lease reports `failed` and the validator issues neither a marker SQL `DELETE` nor restore-resource API `DELETE` requests. Marker cleanup is armed only after the first `INSERT` returns, before commit: a failed `INSERT` rolls back without a cleanup query, but an ambiguous commit still triggers cleanup. The validator publishes `success` only after cleanup succeeds; cleanup errors report `failed-cleanup`.

Existing PVCs do not move automatically. **Before merging the PostgreSQL class change to `main`**, verify that `longhorn-single-node-retain` exists and restore a fresh completed backup into an isolated Cluster on a 40 GiB PVC using that class. Before each replacement, including after switchover, verify Longhorn placement and capacity with the old volumes retained, free space on the surviving PostgreSQL data/WAL filesystems, and a remaining synchronous standby with current sender/receiver streaming and caught-up replay. ## Credentials and bucket separation

A single credential object at OpenBao `kv/platform/r2` is read through separate namespace-scoped Kubernetes auth roles and service accounts. VSO creates distinct destination Secrets. Bucket selection remains declarative and separate for each backup path.

Argo owns the complete `cloudnative-pg/k3s-postgres-backups` ObjectStore as a raw manifest in the existing `k3s-postgres` Application, ahead of the Cluster. The ObjectStore omits `configuration.endpointURL`, which takes a literal, not a Secret reference. The Barman Cloud plugin v0.15.1 copies `instanceSidecarConfiguration.env` to the Barman containers in instance Pods and recovery Jobs. `AWS_ENDPOINT_URL_S3` uses a required reference to `postgresql-r2-credentials:S3_ENDPOINT`; the access key, secret key and region references are unchanged. The endpoint comes from OpenBao through the existing VSO destination, not Git or Argo values. The existing Live raw source for PostgreSQL policy and retention is unchanged and supplies no endpoint.

For this PostgreSQL destination only, VSO rejects missing, empty or malformed endpoint inputs without logging them. The exact accepted form is an HTTPS R2 account URL with a 32-character lowercase hexadecimal account ID, optional `.eu` or `.fedramp` jurisdiction and the exact R2 hostname suffix. No extra URL components, trailing LF, CR or spaces are accepted. Render errors block a Secret update; they do not clear an existing Secret or update running Pod environments. Check successful VSO reconciliation, not just Secret presence. On a separate fresh installation, establish OpenBao custody and the VSO destination before starting backup/recovery workloads. The paired Bootstrap revision retires ObjectStore seed/handoff and handles KV-v2 CAS 0 and OMV rclone custody on that fresh provisioning path, including first-provision resume checks. This is not endpoint or credential rotation.

### Ordered adoption (not authorization)

**Do not merge and auto-sync directly on an existing cluster.** Barman may fall back to AWS S3 if the explicit endpoint disappears before existing containers have adopted the environment reference. A Pod's environment does not change in place. Each phase requires separate approval; this document authorizes no live operations.

1. **Hold, establish custody, then bridge.** Before merging Infra, record the exact Infra, Live and paired Bootstrap revisions. Hold the root `infra` Application **first** (including any upstream reconciliation that could undo the hold); verify no queued or running sync. Then disable automated sync on both `k3s-postgres` and `backup-validation` and verify the same. Leave child reconciliation enabled for the later selective operations. Block competing syncs, manual validator launches and ObjectStore writers. Do not run `gitops-openbao.yml` or any Bootstrap entrypoint during this existing-deployment rollout. With those holds in place, explicitly set `backup-validation/postgresql-restore-validation` (CronJob) to `spec.suspend: true`. Verify suspension, drain all existing validator Jobs and Pods (including manually launched runs), and verify the temporary restore Cluster and ObjectStore are gone. Suspension alone does not stop running Jobs. Keep it suspended through cutover; the old script cannot use the production-only Secret reference in its restore namespace.

   - **Custody gate:** Verify the existing OpenBao version independently without running Bootstrap. Require a fresh successful VSO render/reconcile against that version, not a preexisting Ready condition or Secret. Using protected checks, verify VSO ownership, presence of all required keys, and that the delivered endpoint matches both the verified OpenBao version and the existing literal. No payloads in the evidence. Freeze custody changes after verification. Stop on missing custody or ambiguous evidence; recover custody separately under explicit approval before resuming the rollout. Do not substitute the fresh Bootstrap CAS 0 path.
   - **Maintenance gate:** Before touching the ObjectStore, rehearse the full candidate render, admission and guarded SSA with the installed versions in isolation. Include stale resourceVersion, changed UID and missing-object negatives. Obtain CNPG rollout authorization covering replica rolls that may start on reconciliation (Argo holds do not hold CNPG), supervised primary switchover, and stop criteria for lost quorum, lag or archive failure. Establish baseline replica streaming, lag, quorum, free WAL space and archive health. Do not treat the bridge patch as a read-only staging step.
   - **Bridge write:** Verify the recorded ObjectStore UID, field managers, expected spec and explicit endpoint. Use a separately approved JSON Patch on the existing object, testing `/metadata/uid` against the recorded UID and `/metadata/resourceVersion` against the reviewed snapshot in the same request. Add only the required endpoint env reference and retain the literal and all other configuration. A missing object, UID mismatch, stale version or unexpected spec stops the operation; do not retry blindly or create a replacement. Verify the same UID and only the expected field changes.
   - **Adoption gate:** Complete the authorized CNPG rollout, checking replication and quorum at each step and explicitly completing the supervised primary update. Verify new running instances on the primary and all replicas and the generated recovery Job/Pod specs: exactly one `AWS_ENDPOINT_URL_S3` in each relevant Barman backup/WAL/recovery container, with the required namespace-local Secret reference and no conflicting env override. Complete or retire pre-bridge recovery Jobs before cutover. The updated ObjectStore alone is not evidence of adopted environments. Keep the production literal while completing the [isolated env-only drill](#isolated-env-only-acceptance).

2. **Cut over with all three holds active.** After the bridge and drill pass, merge the verified revision; recheck holds, no pending operations and unchanged Application source lists. Carry out only approved resource-scoped changes using the exact pinned renders:

   - **Validator:** Select only core `ConfigMap` `backup-validation/postgresql-pitr-validator` from the `backup-validation` Application (stable generated name, key `postgresql_restore_test.py`). Verify the operation selects exactly that object. While scheduling remains suspended, verify that the CronJob mounts it at `/validator` and invokes `/validator/postgresql_restore_test.py`. If the CronJob still references an older key, update only that argument with separate approval and verify the argument, script digest and `suspend: true` before resuming. No full Application sync while suspended: its CronJob manifest sets `suspend: false` and can reopen scheduling. No hooks or pruning for this step.
   - **VSO:** Select only `VaultStaticSecret` `cloudnative-pg/postgresql-r2-credentials` from `k3s-postgres` to install the strict template. Require a fresh successful reconcile of this generation against the verified custody version, with the same protected key and endpoint checks, before removing the literal. A rejected input leaves the previous Secret intact; neither that Secret nor an old Ready condition passes the gate.
   - **ObjectStore:** Retain the exact UID, required env reference, legacy custody annotation, `Prune=false,Delete=false` and **50m/64Mi** requests / **250m/256Mi** limits. Adopt the full desired object with the reviewed Argo tracking and field manager, client-side migration disabled and no force, replace or delete/create. Require an atomic expected UID/resourceVersion guard and no create on missing for the adoption write: a preflight GET and an ordinary Argo SSA sync (an upsert) are not such a guard. Use conditional SSA with those metadata preconditions only if the disposable rehearsal proves all three negatives fail without mutation. If the chosen sync path cannot carry and honor the guard, leave the holds in place; use a separately approved guarded adoption path, not a broad child sync. Server-side diff (SSR/ServerSideDiff) is not a write guard, and SSA omission may preserve the literal under another field manager. Inspect actual field presence; if retained, remove **only** `/spec/configuration/endpointURL` with the same separately approved UID/resourceVersion JSON Patch guard. A successful sync or diff is not this postcondition.
   - **Release gate:** Verify actual Argo tracking and desired/live agreement on the same UID, literal absent, unchanged sizing and required refs, healthy VSO, and fresh production WAL archival and a completed post-cutover backup in the intended archive. Recovery is verified only in isolated targets. With the new validator script and fresh local VSO credentials verified, separately approve resuming the CronJob (review missed schedules); only then may full reconciliation be restored. Never print Secret payloads, endpoint literals, full ObjectStore diffs, raw command options or environment dumps.

### Isolated env-only acceptance

Use the pinned CNPG, PostgreSQL and Barman versions, synthetic data, a dedicated R2 test target and separately scoped credentials that cannot access production buckets. Verify the isolated path cannot silently fall back to AWS or use another endpoint source. With the **pre-migration** configuration, complete a named base backup and record its CNPG name and Barman catalog ID; retain it and its WAL. Then migrate the test writer to the env-only store, verify the new Pod environments by reference, and require fresh WAL in the intended R2 archive plus a separate named **post-migration** base backup with a distinct completed catalog ID.

Restore **each** catalog ID into a separate fresh Cluster/PVC set using the candidate `externalClusters[].plugin` source and explicit `recoveryTarget.backupID` plus `targetTime` (not latest). For each backup, commit a unique marker **after** it completes, choose a target between that commit and a second marker commit, and verify the new WAL covering both commits is archived. Verify the selected ID, Ready recovery, expected base data, the first marker present and the second absent by SQL. Do not write to production or reuse its archive as a restore destination.

For plugin recovery, the selected `externalClusters[].plugin.parameters.barmanObjectName` identifies the **authoritative recovery ObjectStore** for catalog, base-restore and WAL configuration. For both restores it must have no explicit endpoint or additional endpoint override and must supply the required `AWS_ENDPOINT_URL_S3` reference to a Secret local to the restore namespace. An endpoint recorded on a historical Backup does not prove which endpoint the plugin used. The scheduled PITR validator deliberately supplies its own explicit endpoint and local S3 selectors and does not pin a base backup ID; it does **not** qualify as this env-only drill.

### Rollback

Before cutover, stop with the explicit endpoint retained and keep all holds. After cutover, reestablish the root hold first, then both child holds, suspend/drain the validator again, and freeze competing writers. In either phase, stop new recovery Jobs and pause/drain endpoint-dependent retention while custody or running env is suspect. Monitor free WAL space and archive failures; do not restart healthy instances just to retry a missing required key.

- **Preferred:** Restore the verified OpenBao inputs through approved custody/version handling (not a direct edit to the VSO destination). Require fresh VSO delivery after the repair. Restart affected containers only via the approved CNPG rollout, including the supervised primary, and regenerate affected recovery Jobs; fixing the Secret does not replace stale env in running containers.
- **Fallback if the endpoint key cannot be delivered safely:** With CNPG rollback rollout authorized and the non-endpoint S3 credential keys verified, atomically restore (or retain) the known-good literal from protected custody and remove **only** the `AWS_ENDPOINT_URL_S3` env entry in a guarded in-place ObjectStore patch. Do not remove the env reference on its own or make it optional. A literal alone does not unblock a Pod with a missing required key; a spec correction alone does not clear stale env from existing Pods. Roll through replicas and supervised primary and recreate affected recovery workloads with the corrected spec. If other required credential keys are missing, stop and recover VSO/custody instead of bypassing it. Keep endpoint-dependent Jobs that still require `S3_ENDPOINT` suspended until that key is restored and their Pods are fresh.

Verify same UID, healthy replication/quorum, fresh WAL and backup evidence plus isolated recovery on the chosen path. Keep automation held until the approved desired state matches that path; do not reapply the old partial SSA manifest, resume the legacy validator, or revive the Bootstrap ObjectStore writer.

No R2 egress restriction is introduced. Configuring the client endpoint is not network isolation.

SMB credentials are separate at `kv/platform/smb`. A dedicated `kube-system` VSO identity materializes `smb-credentials`; the `smb` StorageClass references it for both provisioning and node staging. No SMB credential is stored in either repository.

## Supported K8up transport

The official K8up chart `4.10.0` uses K8up `v2.16.0`. Its API supports `backend.local.mountPath`, `backend.volumeMounts`, `PodConfig`, and one-shot `Backup`, `Check`, and `Prune` resources. The official `csi-driver-smb` chart is pinned to `1.20.3`; its exact values and StorageClass secret parameters were checked against `/tmp/csi-driver-smb-v1.20.3`.

Live's validation PVC and Prometheus repository PVC are dynamically provisioned by StorageClass `smb`, are `ReadWriteMany`, use Kubernetes reclaim policy `Retain` plus driver parameter `onDelete: retain`, and are annotated `k8up.io/backup: "false"` to prevent recursive backup. The inspected chart/driver API supports `subDir`; `${pvc.metadata.namespace}/${pvc.metadata.name}` deterministically maps each retained repository beneath the share. K8up mounts each as its local Restic repository. There is no NFS PV, hostPath, or R2 fallback. Validate SMB dialect negotiation, CSI behavior on every eligible node, retained-subdirectory ownership, UID/GID 1000 permissions, locking, pruning, node loss, and isolated restore before approval.

The validation Schedule keeps 7 daily, 4 weekly, and 6 monthly successful snapshots. A backed-up fixture PVC alone is not a restore test; `backup-validation/k8up-backup-validation` checks its restored marker. See [K8up repository restore tests](k8up-restore-tests.md) for the seeded fixture, restored TSDB read, rollout gates and cleanup. Never overwrite production.

## Prometheus snapshot-first workflow

Prometheus admin API access is enabled. K8up's `PreBackupPod` calls the replica-0 native snapshot API, validates the returned snapshot name, and streams only that snapshot directory to Restic. Its Backup selector matches only the `PreBackupPod`, never the live Prometheus PVC. The exact tool image digest and runtime attachment behavior remain deployment blockers; no image tag or digest is invented.

K8up 2.16 has no conditional post-backup cleanup hook. Therefore cleanup is separate and fail-closed: require `Completed=True` with `reason=Succeeded` on both a uniquely named one-shot Backup and Check, and verify the new K8up Snapshot record before deleting the source snapshot. On any failure, retain it. See [the Prometheus runbook](prometheus-tsdb-backup-runbook.md) for exact native resource templates and the blocked cleanup contract. Restic retention is a one-shot Prune with 7 daily and 4 weekly snapshots.

## Host-side mirrors and remaining recovery gates

Bootstrap defines three mounted-disk-gated systemd services on OMV. Each runs non-destructive `rclone copy` followed by `rclone check --one-way` from `cloudnativepg-backups`, `openbao-backups`, or `etcd-backups` into the same bucket-named directory. Destination ConfigMaps describe this contract but do not perform copies.

Runtime copy evidence, alerts, retention behavior, native K3s S3 upload, isolated restores, and checksum custody are verified by deployed jobs and operational checks rather than pre-deployment gates. Keep R2 credentials (or reissuance access), OpenBao seal/recovery material, the K3s server token, and the K8up repository password in independent encrypted custody. Restore OpenBao first when possible; PostgreSQL and etcd must remain recoverable with an external or reissued R2 credential when Kubernetes and OpenBao are unavailable. Repository changes do not modify the OMV host, cluster, R2, or OpenBao.
