# Compatibility gate

Pinned in the reviewed Infra manifests: Argo CD chart `10.19.1` (Argo CD `v3.6.3`), cert-manager `v1.21.3`, K8up chart `4.10.1` (K8up `v2.16.1`), csi-driver-smb `1.20.4`, Longhorn `1.13.0`, Crossplane `2.5.0`, provider-vault `4.1.0`, OpenBao chart `0.30.8` (OpenBao `2.7.3`), VSO `2.0.0`, CNPG chart `0.29.2` (CNPG `1.30.2`), PostgreSQL `18.7`, Barman plugin chart `0.9.0` (plugin `0.16.0`), prometheus-operator-crds `33.0.2`, kube-prometheus-stack `93.10.0`, and Istio `1.32.0`.

## Upgrade review for November 25, 2026

- Argo CD 3.6 defaults applications with `ServerSideApply=true` to server-side diff. The new chart also renders an application-controller Service and drops the old cluster-scoped notifications RBAC objects. Automatic pruning is disabled for Argo CD, so those RBAC objects require a separate ownership review after rollout. Bootstrap uses the same chart pin and checksum. [Argo CD upgrade notes](https://github.com/argoproj/argo-cd/blob/v3.6.3/docs/operator-manual/upgrading/3.5-3.6.md), [Argo CD release](https://github.com/argoproj/argo-cd/releases/tag/v3.6.3)
- VSO 2.0 serves authenticated HTTPS metrics from the manager on the existing port 8443. The ServiceMonitor still uses the Prometheus account token. Metrics that identify the scraper target by container now use `manager`. The chart ships two external issuer CRDs with cert-manager auto-approval disabled by default. [VSO 2.0 release notes](https://developer.hashicorp.com/vault/docs/deploy/kubernetes/vso/release-notes#vault-secrets-operator-2-0-0)
- cert-manager 1.21.3 removes trust in a compromised root CA and fixes repeated ACME renewal. Crossplane 2.5.0 upgrades stored CRD versions from the configured 2.4 series. Check the activated provider-vault resources after the package manager and RBAC manager have reconciled. [cert-manager release](https://github.com/cert-manager/cert-manager/releases/tag/v1.21.3), [Crossplane release](https://github.com/crossplane/crossplane/releases/tag/v2.5.0)
- The monitoring CRD application precedes the monitoring stack. The operator and CRDs both target 0.95.2. The stack upgrades Prometheus to 3.16.0, Grafana to 13.3.1 and node-exporter to 1.13.1. The operator role gains access to AlertmanagerConfig status and drops permission to delete Pods. [Monitoring chart upgrade notes](https://github.com/prometheus-community/helm-charts/blob/kube-prometheus-stack-93.10.0/charts/kube-prometheus-stack/UPGRADE.md)
- CNPG 1.30.2 adds lease deletion permission via the chart and retries standby streaming during sustained WAL archive recovery. Barman 0.16.0 adds native multi-replica support, and the auxiliary jobs use its matching sidecar image. PostgreSQL 18.7 keeps the Bookworm image variant and updates the restore validator to match. Review affected indexes and take a fresh full backup if incremental backups are in use. PostgreSQL 19 requires a separately planned major upgrade. [CNPG release](https://github.com/cloudnative-pg/cloudnative-pg/releases/tag/v1.30.2), [Barman release](https://github.com/cloudnative-pg/plugin-barman-cloud/releases/tag/v0.16.0), [PostgreSQL release notes](https://www.postgresql.org/docs/18/release-18-7.html)
- K8up 2.16.1 updates Restic to 0.19.1 and the restore adapter uses the same image release. CSI SMB 1.20.4 updates the SMB plugin and CSI resizer. The supported K3s pin remains 1.37.2 with bundled Gateway API 1.6.3. [K8up release](https://github.com/k8up-io/k8up/releases/tag/v2.16.1), [CSI SMB release](https://github.com/kubernetes-csi/csi-driver-smb/releases/tag/v1.20.4), [K3s release](https://github.com/k3s-io/k3s/releases/tag/v1.37.2%2Bk3s1)

## Runtime evidence

Runtime evidence collected automatically during and after deployment:

- Mandatory Kubernetes Berlin timezones require native `admissionregistration.k8s.io/v1` mutating/validating policies and bindings, plus CEL two-variable comprehensions (Kubernetes 1.33+). Production schema/CEL compilation passed with dry-run only; 18 focused checks (4 offline, 14 native admission) passed against isolated agentless K3s `v1.37.1+k3s1`, including forced explicit/imported TZ, init/debug containers and final denial without mutation. All policies fail closed. Production activation, existing-resource adoption and Longhorn/Argo reconciliation remain separate post-merge gates; see `docs/timezone-defaults.md`.
- Istio is pinned to the official `base`, `istiod`, `cni`, and `ztunnel` charts `1.32.0`; Gateway API uses istiod's native automated deployment and `infrastructure.parametersRef` overlays (no separate gateway chart). Local renders and Linux amd64/arm64 image-manifest inspection are static evidence only. The [Istio 1.32 support matrix](https://istio.io/latest/docs/releases/supported-releases/) lists Kubernetes 1.37 and Gateway API v1.6.1; this does not certify the K3s distribution or demonstrate upgrade safety. Verify actual K3s/Flannel CNI paths, kernel/netfilter, ambient traffic, DNS, NetworkPolicy, gateway admission/readiness, three-node scheduling, and Argo child-Application health sequencing. See `docs/mesh-chart-evidence.md`.
- provider-vault `4.1.0` package digest, exact 16-type v2 activation-policy APIs, OpenBao behavior, and drift reconciliation.
- OpenBao snapshot and PostgreSQL retention adapter multi-arch image digests.
- The protected bootstrap ceremony now creates exactly `kv/platform/r2` and `kv/platform/smb`; deployment stays blocked until API and runtime validation confirms CAS-zero behavior and both VSO transformations without exposing values.
- Official csi-driver-smb 1.20.4 runtime compatibility with K3s, SMB dialect/security negotiation, retained dynamic subdirectory behavior, node packages, permissions, failure handling, and the verified mounted OMV backup disk.
- K8up 4.10.1/v2.16.1 native local backend and PodConfig are upstream-supported, but SMB CSI behavior, repository locking/pruning, permissions, independent password recovery, and isolated fixture restore with `k8up-backup-validation` remain deployment-blocking. The repository-defined PostgreSQL/OpenBao/etcd OMV `rclone copy` units still require mounted-disk, checksum, retention, alerting, and restore evidence; see `docs/backup-contract.md`.
- Prometheus snapshot tool image digest, rendered replica-0 PVC identity, native admin-API reachability, same-node RWO attachment, one-shot Backup/Check/Snapshot status verification, exact success-gated cleanup mechanism, isolated restore/checksum, and 7-daily/4-weekly Prune behavior.
- Alertmanager `configSecret` schema plus the OpenBao/VSO `alertmanager.yaml` key and all SMTP values.
- Upstream oauth2-proxy multi-arch digest, OpenBao OIDC compatibility, callback/client contract, and Longhorn-only route isolation.
- Radar image architecture and exact chart values.
- OpenBao/Crossplane/VSO/cert-manager API schema compatibility, including explicit VSO transformations, rotation restarts, provider child-token exchange, every declared policy/auth-role endpoint, and OIDC key/scope/client/provider/group resources for Argo CD, Grafana, Longhorn, and Radar.
- OpenBao first-install behavior with `server.podManagementPolicy: Parallel`, three encrypted PVCs, initialization, Raft joining, automatic unseal, and quorum after restart.
- Longhorn first-install and upgrade behavior with the chart pre-upgrade hook disabled, an explicit supported pre-upgrade check, manager memory headroom, encrypted-volume attach/detach/reattach, and storage cleanup evidence.
- Network-policy behavior after the actual K3s CNI dataplane is installed: namespace selectors, API Service DNAT to port 6443, DNS, operator webhooks, Prometheus scraping, backup jobs, and all stateful clients.
- Verify protected `main` branch rules, reviewed merge history, repository credentials, and Git-revert rollback for Infra, Live, and Apps; force-pushes remain prohibited.
- Barman catalog/delete CLI behavior required by the retention contract and actual PostgreSQL/K8up/OpenBao/Prometheus restore execution rather than manifest-only checks.

Static validation does not claim runtime compatibility. The deployment wrapper performs bounded technical checks, automated restore validation gates deletion, and runtime failures surface as failed workloads or alerts rather than a circular pre-deployment approval gate.
